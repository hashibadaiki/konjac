# 仕組み

翻訳は Preferred Networks の **PLaMo 3 Translate** を、アプリに組み込んだ llama.cpp
（Rust バインディング `llama-cpp-2`）でこの端末の中で動かして行う。外部の API にも CLI にも
投げない。

```
翻訳要求
  → plamo.rs: 言語コードと文体を決め、プロンプト（PFML3）を組む
  → engine.rs: llama.cpp で生成（貪欲デコード）、断片を 1 つずつ画面へ
  → 最後に整えた全文で結果欄を置き換える
```

モデルの重みはアプリに同梱していない。初回に設定画面かダウンロード画面から
Hugging Face の公式 GGUF を落とす（[モデルの取得](#モデルの取得)）。それ以降、翻訳で
ネットに出ることはない。

## モデル

PFN 公式の GGUF（`pfnet/plamo-3-translate-<サイズ>-GGUF`）の **Q4_K_M** を使う。PFN 自身の
クライアント（`pfnet/plamo-translate-cli`）の既定と同じで、PFN によれば Q4_0 は FLORES+ で
BF16 より chrF++ が 0.9 低かったため、とのこと。

| サイズ | 位置付け | ダウンロードの目安 |
|---|---|---|
| 0.8B | 最軽量 | 約 0.6 GB |
| 2B（既定） | 標準 | 約 1.8 GB |
| 8B | 高品質 | 約 5.2 GB |
| 31B | 最高品質 | 約 19 GB |

目安の値は画面に出すための概算で、実際のサイズはダウンロード時に Hugging Face の一覧から取る。

速度の参考として、PFN が M1 Max（llama.cpp、Metal）で測った 2B Q4_K_M の数字は、デコード
毎秒約 111 トークン、最初のトークンまで約 0.28 秒、モデルの読み込み約 1 秒。このアプリ自体で
測った値ではない。

macOS ではモデルの全層を Metal（GPU）に載せる。CPU スレッドは 2 本にしてある — 全層が
GPU にあると CPU が動かすのは入力の埋め込みだけで、PFN の計測では 8 本より 2 本の方が速かった。
Windows / Linux では CPU で動かし、スレッドはコア数の半分。

### 読み込みと保持

モデルは一度読み込んだら翻訳のあとも保持する。2B の読み込みは 1 文の翻訳より長くかかるため。
サイズを切り替えたときは前のモデルを先に捨ててから次を読むので、メモリに 2 つ同時に載ることはない。

起動時、設定でサイズを変えたとき、ダウンロードが終わったときに、選択中のモデルを別スレッドで
先に読み込んでおく。最初の翻訳が読み込み待ちにならないように。失敗してもそこでは何も言わず、
翻訳を頼まれた時点で改めてエラーとして出す。

## プロンプト

PFN のクライアント（`servers/mlx/pfml3.py`。llama.cpp バックエンドも同じものを使う）が組む
PFML3 形式と同じものを組む。改行は説明のためで、実際には入らない。BOS はアプリが自分で先頭に置く
（llama.cpp の PLaMo トークナイザは、GGUF に `tokenizer.ggml.add_bos_token` が無いと付けないため）。

```
<|plamo:bos|><|plamo:tag|>dataset<|plamo:msg|>translation
<|plamo:tag|>input<|plamo:key|>lang<|plamo:val|>en<|plamo:msg|>（翻訳したいテキスト）
<|plamo:tag|>output<|plamo:key|>lang<|plamo:val|>ja<|plamo:msg|>
```

モデルは最後の `<|plamo:msg|>` の後に訳文を書き、制御トークンで終える。翻訳元が「自動検出」の
ときは `input` の `lang` を付けず、モデルに任せる。

### 文体

訳文が日本語のときだけ、`output` に `<|plamo:key|>form<|plamo:val|>polite`（です・ます）か
`plain`（だ・である）を付けられる。この属性は PFN のクライアントには無く、モデルカードの記述と、
綴りが一致している第三者のクライアント 2 つに拠っている。日本語以外が翻訳先のときは文体の
プルダウンを無効にする（モデルが受け付けないので）。

旧版の文体設定は読み込み時に寄せる: `formal` → です・ます、`casual` → だ・である、
`technical` → 自動。

### 日本語を日本語へ

翻訳元が自動検出・翻訳先が日本語で、テキストが日本語に見える（仮名・漢字がラテン文字以上ある）
場合は、**英語へ**訳す。日本語を日本語に頼むとモデルは書き換えてしまうし、日本語の文をコピーして
訳そうとしている人が欲しいのはまず英語なので。PFN のクライアントが方向を自分で決めるときと
同じ判定。こうなったときは結果欄の下に `（日本語 → 英語）` と出す。翻訳元を明示した場合は
言われたとおりにする。

### 言語

画面に出しているのは 15 言語（日本語・英語・中国語簡体字/繁体字・韓国語・仏・独・西・伊・露・
越・泰・インドネシア・アラビア）。モデルカードが挙げる 53 言語に**ポルトガル語が無い**ので、
以前あったポルトガル語は外した。保存済みの設定がポルトガル語を指していれば、読み込み時に
既定（翻訳元は自動、翻訳先は日本語）へ戻す。

## 貼ったテキストに制御トークンが入っていたら

PFML3 の制御トークンはすべて `<|plamo:…|>` と綴られる。貼ったテキストがたまたまそれを含んで
いても（PLaMo についての文書なら普通にありうる）、それが本物のタグとして読まれると、
入力を途中で閉じて自前の `output` を書けてしまう。

なのでプロンプトは 1 本の文字列ではなく区切りごとにトークン化する。

| 部分 | トークン化 |
|---|---|
| プロンプトの骨組み | 特殊トークンを解釈する |
| 貼ったテキスト | **特殊トークンを解釈しない**。`<|plamo:tag|>` は見た目どおりの文字列になる |

ただし「解釈しない」設定だけでは足りない。llama.cpp の PLaMo トークナイザは制御トークンも
普通の語彙と同じ表に入れて探すので、本文に `<|plamo:tag|>` と書いてあれば、その 13 文字を
本物のタグ 1 個として拾ってしまう（極小の偽 GGUF で再現を確認した）。そこで貼ったテキストは
`<|plamo:` の `<` の直後で切ってから区間ごとにトークン化する。1 つのトークンは区間をまたげない
ので、タグとして一致しようがない。それでも制御トークンが出てきた場合は、送らずにエラーにする。

Claude CLI を使っていた頃に翻訳対象をランダムなタグで囲っていたのと同じ役目を、こちらでは
トークナイザの段階で果たしている。そもそも翻訳専用モデルで、道具も実行環境も持たないので、
「指示に従ってしまう」ことの被害も訳文が変になる以上には広がらない。

## ストリーミング

生成したトークンは 1 つずつ Tauri イベント `translate-delta` でフロントに送り、結果欄に追記する。
1 文字が複数のトークンに分かれることがある（漢字や絵文字）ので、UTF-8 として完結していない
バイトは次のトークンが来るまで持ち越してから送る。

```
engine.rs: トークン → バイト → 完結した文字だけ
  → emit("translate-delta", { id, text })
  → main.ts: 結果欄に追記
最後に translate コマンドが返す全文（前後の空白を除いたもの）で結果欄を置き換える
```

`id` はフロントが実行ごとに振る番号で、前の実行の断片が次の結果に混ざらないようにするためのもの。

デコードは貪欲法（毎回いちばん確率の高いトークン）。PFN がベンチマークに使った設定で、
同じ入力なら同じ訳が返る。無応答タイムアウトの設定は無くした — 外部プロセスの起動を待つことも、
ネットワークの向こうで固まることも無くなったので。

## 長い入力

モデルの学習時の長さは入力と出力を合わせて 32,768 トークン。そこで長いテキストは
**段落（空行）ごとに、4,096 トークンに収まるだけまとめて**区切り、1 つずつ訳して元の区切りで
つなぐ。1 段落だけで超える場合は行単位で区切る。改行の無い 1 行がそれだけで超える場合は、
文の途中で切らずにエラーにする（途中で改行を入れてもらう）。短いテキストは 1 つのまま渡るので、
普段はモデルが全体を一度に見る。

各区切りの出力上限は「入力トークン数 × 3 ＋ 256」（学習時の長さを超えない範囲）。
上限に達しても終わりのトークンが来なかったら、訳文の後ろが欠けているので
「訳文が途中で切れました」というエラーにして、そこまでの訳を添えて返す。何も言わずに
欠けた訳を完成品として出すことはしない。

## モデルの取得

```
GET https://huggingface.co/api/models/pfnet/plamo-3-translate-<サイズ>-GGUF/tree/main
  → Q4_K_M の .gguf をちょうど 1 つ選ぶ（分割ファイルは対象外）
  → その LFS の SHA-256 とサイズを控える
GET .../resolve/main/<ファイル名>  → <保存先>/plamo-3-translate-<サイズ>-Q4_K_M.gguf.part
  → サイズと SHA-256 が一致したら .part を外して本来の名前にする
```

- 保存先はアプリのデータディレクトリの `models/`（場所は設定画面に出る）。設定と違って
  開発用ビルドとリリース版で分けていない。中身が同じ数 GB のファイルを 2 回落とす意味が無いので
- 本来の名前のファイルは、常に検証済みの完全なモデル。途中のものは `.part` のまま
- **中止・中断しても `.part` は残す**。次に押すと、それまでの分をハッシュし直してから
  `Range` で続きを取る。サーバが範囲指定を無視して全体を返してきたら最初からやり直す
- サイズが合わなければ「途中で終わった」として `.part` を残し、ハッシュが合わなければ
  どこが壊れたか分からないので `.part` を消す
- 一度に動くダウンロードは 1 つだけ。進捗は `model-download` イベントで 0.2 秒ごとに送る
- 削除はモデルを手放してから消す（Windows は使用中のファイルを消せないため）

## ⌘C ⌘C をどう取っているか

以下は**有効にしたときに何が動くか**の話で、既定では何も動いていない
（[プライバシー](privacy.md)）。

`Cmd+C` をグローバルホットキーとして登録することは **できない** — 登録した時点で全アプリの
コピーを奪ってしまう。かといってキーボードを直接フックすると macOS ではアクセシビリティ
権限が要る。

そこでまず、権限の要らない方式として DeepL と同じ **クリップボードの「変更カウンタ」** を
見ている。同じ文字列を 2 回コピーしても内容は変わらないが、カウンタは書き込みのたびに増える。

| OS | 使っている API |
|---|---|
| macOS | `NSPasteboard.changeCount` |
| Windows | `GetClipboardSequenceNumber()` |
| Linux | 相当するものが無い（X11 は所有権の変化しか出さない）ため非対応 |

60ms 間隔でポーリングして、前回の増加から猶予内（既定 600ms、設定可）に次の増加が来たら
「2 回目」と判定する。アプリ自身が結果をクリップボードに書き戻す分はカウントから
除外してあるので、「自動コピー」を有効にしていても誤爆しない。

キーボードイベントを一切見ないので、**追加の権限は要らない**。

### 音声入力ソフトによる誤爆（クリップボード監視の限界）

変更カウンタには「誰が書いたか」が無い。音声入力ソフト（Aqua Voice, Wispr Flow など）は
文字起こしをクリップボードに置いて ⌘V で貼り、**直後に元のクリップボードを書き戻す**。
1 回の音声入力で書き込みが 2 回起きるので、カウンタだけを見ている側からは
⌘C ⌘C と区別がつかない。実機で「音声入力するたびにウィンドウが出る」のはこれ。

無料で使える手がかりは間隔しかない。**1 回のポーリング間隔（60ms）に 2 回以上**の
書き込みが入ったら、人間の連打ではなくアプリの一括書き込みとして無視する
（⌘C を 60ms 以内に 2 回押すことはできない）。このとき途中まで溜まっていた「1 回目」も
破棄する — 他アプリが置いた内容がユーザーの 1 回目として残らないように。

書き戻しがポーリングを跨いで届いた場合は、これでも取り切れない。内容を読んで
「同じ文字列を 2 回」かどうか確かめれば分かるが、macOS は貼り付け操作を伴わない
クリップボードの読み出しに警告を出すようになったので、毎回のコピーを読むのは採らない
（このアプリがクリップボードの中身を読むのは、いまも 2 回目を検出した瞬間だけ）。

**キーボード監視ならこの問題は起きない。** 音声入力ソフトが送るのは ⌘V であって ⌘C では
なく、キーボード監視は ⌘C のキーコードしか見ないため。誤爆するなら許可を与えるのが早い。

### DeepL と同じ「⌘ 押しっぱなし」に対応する（macOS）

クリップボード監視には限界がある。**⌘ を押したまま C を 2 回**は反応しない — 2 回目の C が
キーリピート扱いになり、コピー元アプリが「同じ操作の繰り返し」としてクリップボードに
書き込まないため。書き込みが 1 回しか起きない以上、クリップボードを見ている側には
検出しようがない。

DeepL がこの操作に対応できているのは、**キーボードイベントを直接監視している**から。
初回起動時に macOS の「アクセシビリティ」許可を求めてくるのはこのため。

なので同じ方式も入れてある。許可があれば `NSEvent` のグローバルモニタで ⌘C の
キー入力そのものを見るので、コピー元アプリが何をしようと関係なく反応する。
初回起動時に macOS のアラートを出すのも同じ理由で、これは一度だけ。アプリが自分を
アクセシビリティの一覧に載せる手段はこれしか無く、尋ねる前に許可画面へ送っても、
そこにはまだこのアプリの行が無い。
数えるのは ⌘ だけを伴う C に限る（⌘⇧C や ⌘⌥C は他アプリのショートカットでコピーではない）。

| | クリップボード監視 | キーボード監視 |
|---|---|---|
| 追加の権限 | 不要 | アクセシビリティ許可 |
| ⌘ を離して 2 回 | ✅ | ✅ |
| ⌘ 押しっぱなしで 2 回 | ❌ | ✅ |
| 音声入力ソフトで誤爆しない | ⚠️ 間隔でしか切れない | ✅ ⌘V は見ない |
| 検出したら | 入力欄に入れて待つ | そのまま翻訳する |
| 対応 OS | macOS / Windows | macOS |

許可があればキーボード監視を使い、無ければクリップボード監視に自動で落ちる
（両方が同時に動いて二重発火することはない）。許可は実行中に与えてもよい。アプリは
2 秒おきに許可の有無を見ていて、与えられた時点でキーボード監視に切り替わり、
クリップボード監視は自分から降りる。アプリ側で何かを押す必要はない
（macOS は許可が変わっても通知をくれないので、見に行くしかない）。

グローバルモニタは**観測専用**で、イベントを握り潰したり書き換えたりはできない。
他アプリのコピーが影響を受けることはない。

コピー元アプリによって挙動が違うので、設定画面に生の値を出してある。
⌘C を押したときに何が起きているかがその場で分かる:

| 表示 | 意味 |
|---|---|
| 検出方式 | キーボード監視 / クリップボード監視 / 停止中 |
| クリップボード変更カウンタ | OS が返す生の値。⌘C で増えなければコピー元が書き込んでいない（キーボード監視中は参照しないので出さない） |
| ⌘C を検出した回数 | ユーザーの ⌘C として数えた回数 |
| 他アプリの書き込みとして無視した回数 | 1 回のポーリング間隔に複数書き込みが入り、連打ではないと判定した回数（キーボード監視中は出さない） |
| 2 回目として起動した回数 | 猶予内の 2 回目と判定してウィンドウを出した回数 |

「⌘C を検出した回数」が増えないならコピー元アプリが書き込んでいない（＝キーボード監視に
切り替えると直る）、増えているのに「2 回目」が増えないなら猶予の問題、押していないのに
「無視した回数」だけ増えるなら他アプリがクリップボードを書いている、と切り分けられる。
操作説明そのものも検出方式に合わせて出し分けているので、いま何が効く操作なのかは
設定画面のチェックボックス直下に書いてある。

## コードの置き場所

プロンプトの組み立て・言語コード・長文の分割・UTF-8 の持ち越しは `plamo.rs`（モデル無しで
テストできる部分）、llama.cpp の呼び出しは `engine.rs`、モデルの一覧・保存先・ダウンロードは
`models.rs` にある。どのモデルで訳すかを決めて三つをつなぐのは `lib.rs` の Tauri `translate`
コマンド。
